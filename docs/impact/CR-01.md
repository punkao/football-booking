## 3. Impact (ก่อน diff)

### 3.1 แบบที่เลือก

1. **token ใหม่ไม่ซ้ำต่อการเข้าสู่ระบบ:** `sign({ cid|sid, jti, exp })` · `jti` สุ่ม 16 ไบต์ · `exp` = เวลาเข้าสู่ระบบ + อายุเดิม (30 วัน / 12 ชม. = เท่า `Max-Age` เดิม → ไม่เปลี่ยนอายุ `[D:CR-01]`) · ชื่อ cookie และ flag เดิมทุกตัว
2. **รายการยกเลิกฝั่ง server:** ตาราง `revoked_sessions(token_hash, kind, expires_at, revoked_at)` · `token_hash` = SHA-256 hex ของค่า cookie ทั้งก้อน (**ไม่เก็บ cookie ตัวจริง** · CHECK `^[0-9a-f]{64}$`) · logout = INSERT แถวของ token ที่ใช้ออก (ถ้ายังใช้ได้) + ลบแถวที่เลยเวลาหมดอายุแล้ว
3. **ทางตรวจเดียว:** `checkSession` ใน `web/lib/server/core.ts` (ลายเซ็น → รูปแบบ → หมดอายุ → อยู่ในรายการยกเลิกไหม) · `customerIdFrom` และ `staffFrom` เรียกตัวนี้เท่านั้น · ส่วนอ่าน payload เป็นฟังก์ชันบริสุทธิ์ `readSession` ใน `crypto.ts` (unit test ได้โดยไม่มี DB)
4. **cookie แบบเดิม (ก่อนอัปเดต) ใช้ต่อได้ `[D:CR-01]` Q2:** รูปแบบ `{cid}` / `{sid}` (key เดียวพอดี) รับต่อถึง `applied_at` ของ migration 007 + อายุเดิม (30 วัน / 12 ชม.) · cookie แบบเดิมทุกใบในเบราว์เซอร์หมดอายุก่อนเวลานั้นแน่นอน (ออกก่อนอัปเดต) → ไม่มีใครถูกบังคับเข้าใหม่ · หลังเวลานั้นปฏิเสธ (ปิดรู "cookie ที่ขโมยไปใช้ได้ตลอดไป") · logout ด้วย cookie แบบเดิม = ยกเลิกค่านั้น (`expires_at` = เวลาสิ้นสุดเดียวกัน) → ล้างแถวได้
5. ตรวจ payload เข้ม: id ต้องเป็นจำนวนเต็มบวก · ชุด key ต้องตรง (`{cid}` หรือ `{cid,jti,exp}`) → draft แชท (`{kind,sid:string,a,exp}`) · `ln_access` (`{codes}`) · cookie ร้านใส่ช่องลูกค้า ใช้แทนกันไม่ได้
6. เวลาหมดอายุ session ใช้ **เวลาจริง** (`Date.now()` / `now()` ของ DB) ไม่ใช้นาฬิกาแอป `app_settings.clock` (ADR-04 = เวลาธุรกิจ ล็อกไว้ 9 ต.ค. ในเครื่องทดสอบ · ถ้าใช้ จะเลื่อนเวลาให้ session ที่หมดอายุกลับมาใช้ได้)

ทางเลือกที่ไม่เลือก: ตาราง `sessions` เต็มรูปแบบ (ทุกคำขอต้องมีแถว → cookie แบบเดิมไม่มีแถว = ทุกคนต้องเข้าใหม่ ขัด Q2 และ backfill ไม่ได้เพราะไม่รู้ว่ามี cookie อะไรอยู่บ้าง) · เปลี่ยน `SESSION_SECRET` (ทุกคนหลุด ขัด Q2) · เก็บใน memory (หายตอน restart · หลาย instance ไม่เห็นกัน)
